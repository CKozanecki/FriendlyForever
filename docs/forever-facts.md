# WoW Forever facts

Game and API facts the addon's code depends on, so each session doesn't have to research them again. **Facts only:** each one gives its source, or the issue where it was researched and sourced. The launch-day checks (Nov 4) were completed in game and worked (#197), except the four IDs below that nobody could reach and the Salvation, Mass Salvation and Revoke checks (Blizzard removed those spells, #208): the facts that worked are marked **confirmed in game**, with their sources kept. A fact nobody has confirmed goes on a new issue labelled `quality`, with its source and how to check it in game, and is marked here with a link to that issue (four map and instance IDs the owner can't reach yet are on #207). Three facts that #50's list didn't name were settled by the owner on Nov 8 (#197): the `/say` rule, the spell IDs and the mana classes, each with the owner as its source below. Blizzard removed Salvation, Mass Salvation and Revoke right before launch (owner, 2026-11-08); their lines below keep their beta sources, and the code is #208's.

WoW Forever isn't Classic Era (AGENTS.md's "Issues and specs"). Check new facts against Forever sources (Wowhead's `/forever/` pages, patch notes), put the sources on the issue, and add the fact here in the same PR. When an unconfirmed fact is settled in game, mark its line confirmed here. Where this file and CONTRIBUTING.md differ, CONTRIBUTING.md wins and this file is fixed.

Many sessions couldn't reach wowhead.com or warcraft.wiki.gg and used web search instead; the issues say which.

## The client

- Forever is client 1.60.1, interface `16001` (the TOC's `## Interface`), with the retail UI and the addon compartment. Source: #93 ([TOC format](https://warcraft.wiki.gg/wiki/TOC_format); Forever addons on CurseForge such as [Forever LazyChatButtons](https://www.curseforge.com/wow/addons/forever-lazychatbuttons)). Whether the compartment is there: **confirmed in game** (launch, Nov 4).
- It uses the modern (12.x) API, with Midnight's addon restrictions. Source: [#32](https://github.com/CKozanecki/FriendlyForever/issues/32#issuecomment-6484071238) ([classicwowforever.com](https://classicwowforever.com/guides/wow-forever-addons-api-compatibility/), [Patch 12.0.0 planned API changes](https://warcraft.wiki.gg/wiki/Patch_12.0.0/Planned_API_changes)); community sources, no blue post.
- Addons ship their own icons as TGA through `## IconTexture`; the game loads TGA and BLP reliably, not PNG. Source: #65, #93. How the icon looks: **confirmed in game** (launch, Nov 4).

## Secret values

- In restricted moments the game hands addons **secret values**. Addon code must never compare, index, measure, concatenate or send one; it tests for them with `issecretvalue` and `issecrettable` (`Util.IsSecret`, `Util.Readable`). Source: #32 (Midnight's rules, sources above); AGENTS.md's "Secret values".
- Chat received inside an instance can arrive as secret values. Source: #32. Whether it does: **confirmed in game** (launch, Nov 4).
- Whether your own PvP flag, and other players' flags and names, are secret, and when: **confirmed in game** (launch, Nov 4). The addon reads them as possibly secret. Source: as built for #27 and #30 (`Offers.lua`, `GroupBuffs.lua`).
- Whether group members' roles and aura casters are readable: **confirmed in game** (launch, Nov 4) (from #68).
- In a fight, the player's own `UNIT_AURA` updates reach addons restricted: their fields (or the whole payload) are secret, one per aura update. Source: the owner's debug log, in game, 2026-11-12 (#268). A buff that lands then can't be read from its update, so `BuffTracker` looks at every buff as the fight ends, or at the next update it can read, and handles the ones it missed then (#245). That the game's own list (`C_UnitAuras.GetAuraDataByIndex`) is readable again once the fight is over is **unconfirmed**; #334 says how to check it in game. If the game refuses the list then (an error), a missed buff is read at the next update the addon can read; entries it lists but the addon can't read out of a fight are let go, as before.

How the simulated client models secrets, and its limits, is in [simulated-client.md](simulated-client.md).

## Chat

- A chat message is at most 255 bytes (`Util.MAX_CHAT_BYTES`), and may not contain `|` escape codes. Source: as built since #20; the simulated client enforces both.
- Addons may use `/say` outdoors only right after a key press (a hardware event); inside instances they may use it freely. Source: [Patch 8.2.5 API changes](https://warcraft.wiki.gg/wiki/Patch_8.2.5/API_changes); as built (README's Buff thanks, `ChatQueue.lua`). Confirmed in game: the owner tested it before the beta ended (Nov 8).
- A press of the buff-back button (`BuffButton.lua`), on any binding, the mouse wheel included, or a mouse click on it, releases a held `/say` from the down half's PostClick, in the same press that casts (#271). That the game counts that PostClick as inside the hardware event for `SendChatMessage`: **unconfirmed**; #275 says how to check it in game. The reasoning: the secure cast that same press makes also needs a hardware event, and it works on the wheel (confirmed at launch, #28). A click from code (`Button:Click`) arrives as an up half, so it releases nothing.
- Before #271, only a keyboard key (`OnKeyDown`) released held `/say` lines: a buff-button press on the mouse wheel fires no `OnKeyDown`, so the thank-you waited for a later key (owner, in game, 2026-11-12).
- An ordinary mouse click on the game world: whether a `GLOBAL_MOUSE_DOWN` handler counts as a hardware event is **unconfirmed**, so it doesn't release held lines yet (#275).
- Text emotes (`/thank`) do **not** need a key press (owner, in game, 2026-11-09). As built since #236, emotes go out at once; only `/say` and `/yell` wait for a key press (`ChatQueue.NeedsHardwareEvent`).
- Whether `C_ChatInfo.PerformEmote("THANK", unit)` (with `DoEmote` as the fallback) is aimed at that unit. Source: #52. **Confirmed in game** (launch, Nov 4).
- `CHAT_MSG_WHISPER`, `CHAT_MSG_SAY` and `CHAT_MSG_PARTY` (`CHAT_MSG_PARTY_LEADER` from the party's leader) give the text first and the sender's name second, as in the retail API ([CHAT_MSG_WHISPER](https://warcraft.wiki.gg/wiki/CHAT_MSG_WHISPER), [CHAT_MSG_SAY](https://warcraft.wiki.gg/wiki/CHAT_MSG_SAY)). Buff requests (#40) assume the sender is the whole name (`First-Surname` or `First Surname`, as `CHAT_MSG_ADDON` gives, #138) and ignore a sender with no surname. That form for these events, and that their text is plain in the open world: **unconfirmed**; #352 says how to check them in game.
- The game has a chat lockdown (`C_ChatInfo.InChatMessagingLockdown`); nothing is sent while it's on. Source: #32. Whether it covers addon messages: **confirmed in game** (launch, Nov 4).
- Raid join messages do appear on Forever: the maintainer saw them on the beta, 2026-10-22. Source: #15.

## Addon messages

From #32 ([research comment](https://github.com/CKozanecki/FriendlyForever/issues/32#issuecomment-6484071238); [SendAddonMessage](https://warcraft.wiki.gg/wiki/API_C_ChatInfo.SendAddonMessage), [Patch 10.2.7 API changes](https://warcraft.wiki.gg/wiki/Patch_10.2.7/API_changes), [Icy Veins: combat restrictions eased](https://www.icy-veins.com/wow/news/combat-addon-restrictions-eased-in-midnight/)). Every item here is **confirmed in game** (launch, Nov 4) (the #32 checks).

- Since 10.2.7, `C_ChatInfo.SendAddonMessage` is throttled per prefix: 10 messages, refilled at 1 a second. The server can change these numbers at any time (#32).
- A throttled send returns `Enum.SendAddonMessageResult.AddonMessageThrottle`; 0 means success (#32).
- A prefix is at most 16 characters, and a message at most 255 bytes (#32).
- Under Midnight's rules addons may not message other players inside instances (on live: boss encounters and Mythic+) (#32).
- Guild addon messages come back to their sender, and every guild member, the sender included, gets the guild's addon messages in the same order: the order the server relays them. A message is relayed to everyone or lost for everyone. Guild hellos' cap (#38) relies on all three: a copy greets only once its own `GREET` is back with fewer than K others before it. Until one of its own has come back in a session (the game might not send them back, or might spell our name differently), a `GREET` that never comes back still greets, after the random wait, so this can't silence every hello. Source: #32 (they come back), #38 (the order). **Confirmed in game** (launch, Nov 4).
- Message types so far: `HELLO` (#32); `ANSWER` (#37), whispered to a player whose favour you just returned, so their copy doesn't owe you one back; `PLAN` (#36), whispered to a player you're exchanging buffs with, naming the buff your button holds for them; `RECEIPT` (#138), whispered to a player outside your group your buff just landed on, so their copy can name you when their game can't; `GREET` (#38), sent to the guild by a copy about to greet a guildmate who logged in, with the line it picked; and `SHARE` (#70), sent to the raid on joining, on roster changes, every 60 seconds and after each fight, with the buff keys a copy gives, its hand-set Blessings and a flag asking the others to answer (the raid buff split). Whether an addon whisper reaches a stranger nearby decides whether `ANSWER` and `PLAN` work at all; without them, buff back still stops after one round within its 10-minute window (#37), and a thank-you waits only up to its 5-second cap (#36). Confirmed in game (launch, Nov 4) (#37, #36).
- The sender name's form in `CHAT_MSG_ADDON` (`First-Surname` or `First Surname`), and whether an addon whisper reaches a stranger nearby (#32). Receipts depend on both, and on whether a stranger's aura caster really is unreadable, which decides how much they help (#138). Confirmed in game (launch, Nov 4) (#138).
- Receipts are never sent inside any instance: the addon reads `IsInInstance()` and counts an unreadable answer as inside, the pessimistic reading of Midnight's rule above (#138).

## Names and races

- Every character has a first name and a surname (`Nikki-Shifts`), with no realms, and the game can't find a player by first name alone. Source: [Icy Veins: names in Forever](https://www.icy-veins.com/wow-forever/news/names-are-different-in-wow-forever-here-are-the-rules-and-the-official-look/); as built (README, `Util.lua`). How `/targetexact` spells a two-part name, and how `UNIT_SPELLCAST_SENT` gives the target: **confirmed in game** (launch, Nov 4).
- Until a group member's details load (just after they join), the client can name them `UNKNOWNOBJECT` ("Unknown" in English), and the addon treats that as no readable name (`Util.UnitFullName`). Source: #99, found by the UI simulator (#83, PR #96); the default UI's `UNKNOWNOBJECT` global string. What Forever's `UnitName` returns then (with or without a surname, secret or not), and whether `UNIT_NAME_UPDATE` fires when it loads: **confirmed in game** (launch, Nov 4).
- There are 10 playable races: Classic's eight plus the two Skyborne peoples, High Order (Alliance) and Windshaper (Horde). Source: [#52](https://github.com/CKozanecki/FriendlyForever/issues/52#issuecomment-6484052636) ([Warcraft Tavern: races](https://www.warcrafttavern.com/forever/guides/races/), [seemeta](https://seemeta.com/en/wow-forever/races)).
- The Skyborne share one race file name; the addon tells them apart by race ID 95 (High Order) and 96 (Windshaper), with the faction as the fallback. Source: #52 (no external source for the IDs). The race and ID in `/friendly status`: **confirmed in game** (launch, Nov 4).

## Resting

From #449 (2026-11-17), read from Blizzard's Forever UI code: Gethe/wow-ui-source at `aff0d8cd53bf4d9ef1c1dd2786b94461a276fb16` ("1.60.1 (70707)", the UI simulator's `BLIZZARD_UI_COMMIT`). warcraft.wiki.gg and wowhead.com could not be read from the cloud session; web search found only old pages (wowprogramming's `IsResting`, which gave `1` or `nil` in old clients).

- `IsResting()` takes no arguments and returns a `bool` that is never nil (`Nilable = false`), with no secret-return flag (`Blizzard_APIDocumentationGenerated/PlayerScriptDocumentation.lua`). Blizzard's own UI calls it bare, with no `issecretvalue` check: the player frame's rest icon (`Blizzard_UnitFrame/Mainline/PlayerFrame.lua`), the experience bar's rested tooltip (`Blizzard_StatusTrackingBar/Mainline/ExpBarOverrides.lua`) and the War Mode button (`Blizzard_PlayerSpells/PvPTalents/Blizzard_WarmodeButtonTemplate.lua`) (#449).
- `PLAYER_UPDATE_RESTING` is a synchronous event with no payload (`UnitDocumentation.lua`). The player frame redraws its rest icon on it, and the experience bar and the honor bar register it too (#449).
- The addon reads it through `Util.ReadGameValues` all the same, and anything but `false` counts as resting (`WeaponBuffs.lua`): the pessimistic reading, in case Forever hands it out as a secret after all (#449).
- **`IsResting()` is true in an inn:** confirmed in game in Brill's inn on 18 Nov (the owner and the game watcher, 1.4.3). Elsewhere (capitals, Valanaar, a Camp Tent, walking out of a town) it is unconfirmed: #450 was closed unchecked, and the addon works from player feedback.
- Buff mode's passers-by (#484, the owner): where `IsResting()` is true, or can't be read, a passer-by never turns buff mode on or keeps it on (`BuffModeAuto.lua`).

## Buffs

From #68 (beta build 70425, mid-October 2026; [Paladin deep dive](https://www.wowhead.com/forever/blue-tracker/news/eu/world-of-warcraft-forever-class-deep-dives-paladin-world-of-warcraft-blizzard-24302099), [Blessing of Salvation (Forever)](https://www.wowhead.com/forever/spell=1038/blessing-of-salvation), [paladin talent calculator](https://www.wowhead.com/forever/talent-calc/paladin), [forg.gg build 70425](https://forg.gg/en/forever/tips/build-70425)). These are beta sources; the role-API check below was **confirmed in game**; the Salvation, Mass Salvation and Revoke checks no longer apply, because Blizzard removed those spells (launch, Nov 4).

- **Blessings last 1 hour,** up from 5 or 15 minutes (#68).
- **Salvation isn't a Blessing** (removed by Blizzard right before launch, tank threat was buffed instead: owner, 2026-11-08; the addon no longer offers it: #208): a member can wear your Salvation and one of your Blessings. Salvation (spell 1038) cuts the target's threat by 30% for 1 hour, on a party or raid member; it's learned at level 26 (#68).
- **Mass Salvation** (removed by Blizzard right before launch: owner, 2026-11-08) (formerly Greater Blessing of Salvation) covers every member of the target's class in the group; learned at level 60, it uses a Symbol of Kings. The addon only skips an aura with Classic's ID, 25895 (`BuffData.IsRemoved`, #208) (#68).
- **Revoke** is new at level 26: it takes Salvation or Mass Salvation off a party or raid member (instant, 40 yards, no cooldown). Blizzard removed Revoke right before launch (owner, 2026-11-08); the addon no longer offers it (#208). Its spell ID was never recorded (#68, #74).
- Which role APIs exist (`UnitGroupRolesAssigned` or `GetPartyAssignment("MAINTANK", unit)`) (#68): **confirmed in game** (launch, Nov 4).
- **`UnitGroupRolesAssigned` gives `"HEALER"` and `"DAMAGER"`** (as well as `"TANK"`) for group members once the group's roles are chosen; until then a member's role is `"NONE"`. Source: the owner, 2026-11-15, who uses an addon that finds healers this way (#408); the API's values (TANK, HEALER, DAMAGER, NONE) are as [API UnitGroupRolesAssigned](https://warcraft.wiki.gg/wiki/API_UnitGroupRolesAssigned) lists them (read from search results on #408). The addon's who-gets rules by role (Tanks, Healers, Damage) read it (`BuffRules.Role`); a member with no role chosen has no role, and one whose role can't be read gets no buff by role.
- The buff spell IDs in `BuffTable.lua` are generated from Forever's own spell data, once per game version, never looked up while playing (#209; owner, Nov 8). Source: upstream's `wow-cli casc sync-forever-spells` (Osso/wow-ui-sim, commit 1a080c3) on build 1.60.1.70685, file SHA-256 `13122873d813481e85815946ddf964068b04132d4d2b2b44ba5ce61491595ad0` (`scripts/data/forever-spells.json`). Every rank and group ID we had from Classic is in that data with the same ID and name. Three facts about the data: **the data still has rows for removed spells** (Salvation 1038, Mass Salvation 25895, and Blessing of Light 19977-19979 and 25890), so "in the data" does not mean "players can learn it", and the generator keeps an explicit exclusion list of spells Blizzard removed, in `scripts/spell-buffs.json` (Blizzard removed Blessing of Light too: owner, 2026-11-09, citing [Blizzard's WoW Forever beta development notes, updated November 2](https://us.forums.blizzard.com/en/wow/t/wow-forever-beta-development-notes-–-updated-november-2/2360696/9); #237); the scroll spells (8096-8101, 8112-8114, 12176-12178) are in four of the five tables but have no `SpellPower` row, so upstream's tool refuses them, and the owner decided scrolls never count as a buff anyway (2026-11-09); reagents are items, which the extraction does not cover, so they stay hand-listed (#225; their IDs were checked against Forever's own data on 16 Nov 2026: see "Data research of 16 Nov 2026").
- **The self-buffs' spells** (#44 part 2, 2026-11-14) come from a second, larger extraction, `scripts/data/forever-spells-extended.json`, file SHA-256 `43d0cfa0a207b9fc0bc9ae5ea76b70b3d2ecb8779f4b33b92e288ce45d7cc45b`, which `scripts/gen_spell_table.py` reads; `scripts/data/forever-spells.json` stays as it was, the copy the UI simulator checked until #343. Since #343 the UI simulator downloads this larger file itself, with the same IDs added before its build, and pins its hash (`SPELL_DATA_SHA256`, `43d0cfa0…`); its first run there, at `9c48956` (#308), matched it byte for byte. How it was made: upstream's `wow-cli casc sync-forever-spells` at Osso/wow-ui-sim `936d5f5` (the commit the UI simulator pinned then, its download code reviewed on #160 and unchanged up to `9c48956`, #308), with the 71 spell IDs of #44's self-buffs (Aspect of the Cheetah, of the Pack and of the Beast included, for the `aspect` family) added to upstream's `data/forever-spell-ids.txt` (its 74 IDs kept), 145 in all; nothing else in upstream's source changed. It was built with Rust 1.99.1 and upstream's locked crates, offline, with no network, an empty environment and no secrets, as an unprivileged user; it downloaded as that user in an empty network namespace whose only way out was a relay that allowed nothing but an HTTPS tunnel to the four hosts CI allows (`us.version.battle.net`, `level3.ssl.blizzard.com`, `us.cdn.blizzard.com`, `kr.cdn.blizzard.com`) on port 443; it used the first two. The evidence: the same build with upstream's 74 IDs unchanged made a file with exactly the SHA-256 the UI simulator pinned then (`SPELL_DATA_SHA256` before #343, `baafb936…`), two runs of the extended build made identical files, and `scripts/sim-spell-check.py` finds all 72 spells of `forever-spells.json` with the same rows, tables and build in it (`spec/bufftable_spec.lua` runs that check). The tool reads tables pinned by content key to build 1.60.1.70685 (build key `002a8047a7c3a53de5e981936db76cce`), and refuses a selected spell that is missing or in an encrypted range: none was. **Every self-buff spell is on Forever at Classic Era's ID and name**, Aspect of the Hawk rank 7 (25296) included, with Classic's rank order. **Two of them aren't Classic's spells, though** (#363's architecture review, from the extracted rows):
  - **Omen of Clarity (16864) is a passive:** its `SpellMisc` row has the passive attribute (`Attributes_0` 64), no duration (`DurationIndex` 0), no `SpellPower` row (no cost), and the passive's text ("Your spells and attacks have a chance to grant you Clearcasting…"). On Classic it's a 10-minute buff you cast. Source: the committed extraction's rows, read on #363 (#44).
  - **Trueshot Aura is a timed buff:** 19506, 20905 and 20906 have `DurationIndex` 30, the same as Righteous Fury and the armors (30 minutes), and "Lasts $d" in their text, where Classic's is an aura that stays on. Forever labels them "Rank 3" to "Rank 5" (Classic's ranks 1 to 3). **Ranks 1 and 2 are 1299346 (level 25, 180 mana) and 1299348 (level 32, 245 mana)**, also 30 minutes: read from build 1.60.1.70938's data on 16 Nov 2026 (#379, "Data research of 16 Nov 2026" below). A third-party Forever database had given rank 1 as 1299346 ([gamemaps.net](https://www.gamemaps.net/game/wow_forever/spells/1299346-trueshot-aura), [metaforge.app](https://metaforge.app/wow-forever/database/spells/hunter-trueshot-aura?v=1299346)); the data agrees. Both are above a million, which is why the generator's ID cap is 10,000,000 (it was 1,000,000, 10,000,000 since #350). They aren't in the committed extraction, so `scripts/spell-buffs.json` hand-lists them (`handRanks`) after ranks 5 to 3; the next extraction can add them to `scripts/data/forever-spell-ids-extra.txt`, and the generator then says to drop `handRanks`.

  **The owner's decisions** ([#44](https://github.com/CKozanecki/FriendlyForever/issues/44#issuecomment-6878196920), 2026-11-14): Omen of Clarity isn't offered (its key stays known, in `scripts/spell-buffs.json`'s removed list, and its passive's aura is passed over), and Trueshot Aura is a timed self-buff like Battle Shout (anyone's copy counts, topped up under the usual rule), offered at ranks 1 to 5 (1 and 2 since #379).

  The extraction selects spells by ID, so it can't show a Forever rank whose ID Classic doesn't have. Reading a spell's `DurationIndex`, its passive attribute and gaps in its rank labels is how to see changes like these two. The durations the indexes stand for were read from spells whose duration is known: 42 is an hour (Blessings), 6 is 10 minutes (Inner Fire, Thorns), 25 is 2 minutes (Battle Shout), 21 never runs out (Aspects, paladin auras) and 30 is 30 minutes (Righteous Fury, the armors). The in-game checks are on #326.
- **Unending Breath** (warlock, 5697) has no group version. Spell 131 is the **shaman's** Water Breathing, which also lets the target breathe underwater, so `BuffData` lists it as a blocker (wearing it counts as having Unending Breath), not as a group version a warlock could cast. Source: [#135](https://github.com/CKozanecki/FriendlyForever/issues/135) ([Unending Breath](https://warcraft.wiki.gg/wiki/Unending_Breath), [Water Breathing](https://warcraft.wiki.gg/wiki/Water_Breathing), [classicdb 5697](https://classicdb.ch/?spell=5697), [classicdb 131](https://classicdb.ch/?spell=131)); Classic sources, as wowhead.com couldn't be reached. - **Water Breathing** (shaman, 131) is a buff the addon offers since #136: on Classic it's one rank, learned at level 22, lasting 10 minutes, at 30 yards, with a Shiny Fish Scales reagent. Source: [#136](https://github.com/CKozanecki/FriendlyForever/issues/136) ([Water Breathing](https://warcraft.wiki.gg/wiki/Water_Breathing), [WoWClassicDB 131](https://wowclassicdb.com/tbc/spell/131), [Vanilla WoW Wiki](https://vanilla-wow-archive.fandom.com/wiki/Water_Breathing)); Classic sources, found by web search, as wowhead.com couldn't be reached. Its ID, ranks and reagent on Forever: **confirmed in game** (launch, Nov 4) (#136).
- **Water Walking** (shaman, 546) is offered only when a player asks for it in chat (#40; the owner's decision on [#350](https://github.com/CKozanecki/FriendlyForever/issues/350#issuecomment-6872373250), 2026-11-14): buff back and buff mode never offer it unasked, and the water rule doesn't apply. **The shaman's spell is 546 on Forever.** Source: the owner, 2026-11-14, from [Wowhead's Forever page](https://www.wowhead.com/forever/spell=546/water-walking) (#350). **Other spells give Water Walking on Forever:** an item's effect, 1299351, and two potions' effects, 11319 and 1310296 (same source). A player wearing any of the four already has it, and their request counts as met (the owner's decision on #350): `BuffTable.lua` lists the three as blockers of 546, as Water Breathing and Unending Breath block each other. They are never cast, and knowing one isn't knowing the spell. The addon then offers it only when the client names spell 546 exactly "Water Walking". A wrong ID could never be offered, and "/cast" casts by that name, never another spell. A client in another language doesn't offer it (#350). The next extraction can add the four IDs to `scripts/data/forever-spell-ids-extra.txt`; the generator then says to drop the hand-listed ranks. 1299351 and 1310296 are above a million, so the generator's ID cap is 10,000,000 (it was 1,000,000).
- **Near water** (#136): the addon reads `IsSwimming()`, `IsSubmerged()` and the breath bar (mirror timer `"BREATH"`, `GetMirrorTimerInfo`, `MIRROR_TIMER_START` and `MIRROR_TIMER_STOP`), which the modern API has; there's no call for whether another player is swimming. ## Rank levels (#459)

- **The levels** (#459, 17 Nov 2026): each rank's level, `SpellLevels.SpellLevel`, for every rank and group version in `BuffTable.lua` (136 spells), in `scripts/data/forever-spell-levels.lua`, which `scripts/gen_spell_table.py --levels` copies into the table as each buff's `levels`. Read from Blizzard's CDN (`us.cdn.blizzard.com`, product `wowf`) with `scripts/read_spell_levels.py`, written for this and run from a session, standard library only, nothing from upstream built or run: at **build 1.60.1.70959** (build config `ad887adcf63b8746155dd40e1930b80f`, CDN config `4831465d4b6a7db3302338ab0f1ac231`, the US build that day) and again at 1.60.1.70938 (`3627b099867bfde3e37a17cf44f69cdc`, the EU one), whose rows are identical. `SpellLevels.db2` is file data ID 1140079 (the wowdev community listfile), layout hash `7EB86FDC`, 13,002 readable rows (69 more are in encrypted sections, none of ours); its SHA-256 is `1e7b93596831e19ce60df01510cc546cbaf7dcb14fb2bdfab573a3eee86d6832` in both builds, the same file whose prefix #379's research recorded at 70938, which confirms the file ID. Each of our spells has exactly one row (difficulty 0), and every level recorded before agrees: Trueshot Aura 25, 32, 40, 50 and 60 (#379), and the group versions' levels (#202). The values are Classic Era's: Mark of the Wild 1, 10, 20, 30, 40, 50, 60; Thorns 6 to 54; Power Word: Fortitude 1, 12, 24, 36, 48, 60; Arcane Intellect 1, 14, 28, 42, 56; Blessing of Kings 20; Divine Spirit 30 to 60; Shadow Protection 30, 42, 56. Water Breathing, Unending Breath and Water Walking have `BaseLevel` 0 and `SpellLevel` 22, 16 and 28: the rule reads `SpellLevel`.
- **The rule:** a rank reaches another player only when **their level + 10 is at least the rank's level**; a higher rank is refused with "Target is too low level" (`SPELL_FAILED_LOWLEVEL`). Source: the server's rule as Classic's emulators have it, cmangos-classic's and vmangos's `SpellMgr::SelectAuraRankForLevel` (`if (level + 10 >= spellInfo->spellLevel) return spellInfo;`), which `Spell::CheckCast` uses to refuse a rank above it ([cmangos-classic SpellMgr.cpp](https://github.com/cmangos/mangos-classic/blob/master/src/game/Spells/SpellMgr.cpp), [vmangos SpellMgr.cpp](https://github.com/vmangos/core/blob/development/src/game/Spells/SpellMgr.cpp)). So the Mark of the Wild rank 7 (level 60) reaches a level-50 player, and rank 6 (level 50) a level-40 one. On Forever the owner's test (17 Nov, #459) showed a macro's unranked cast refused on low players, and no rank chosen for them. The margin, the macro's `Spell(Rank N)` and the rank text are **unconfirmed** on Forever: [#463](https://github.com/CKozanecki/FriendlyForever/issues/463) says how to check each. A group version's rule on a low-level member is unknown too (#463).
- **What the addon does** (`BuffData.CastFor`, #459): a buff for another player is cast at the highest rank you know whose level is at most theirs + 10. When that is your highest rank, by its plain name, `/cast [help,nodead] Mark of the Wild`, as 1.4.1 did; only when stepping down for a low-level player by name and rank, `/cast [help,nodead] Mark of the Wild(Rank 5)`, with the rank text the client gives (`C_Spell.GetSpellSubtext`, else `GetSpellSubtext`; on Forever only the first exists, see "In-game pass of 18 Nov"). The owner's decision on #459 (17 Nov): the rank text and `Spell(Rank N)` are unconfirmed, so only a cast 1.4.1 couldn't make depends on them. A buff of one rank (Blessing of Kings, whose data has no rank text) is cast by its name. A player whose level the game won't give as a whole number from 1 to 80 (`UnitLevel`: a secret, nil, or -1 for "??") is offered nothing, and the button says "can't see their level". Your own copy (buff mode) is your highest rank, by its plain name: your level allows every rank you know. Self-buffs, weapon buffs and group versions are cast as before.

## Druid forms (#452)

From #452 (17 Nov 2026). Researched from Forever's spell data, two open-source Classic server cores and Blizzard's UI source. The wikis can't be reached from a cloud session.

- **No buff can be cast in a form.** In Forever's data (build 1.60.1.70685, `SpellMisc` in `scripts/data/forever-spells-extended.json`), every rank of Mark of the Wild, Gift of the Wild and Thorns has bit `0x00010000` of `Attributes_0` set, and so does every other buff the addon casts (#452).
  - **What the bit means:** cmangos-classic names it `SPELL_ATTR_NOT_SHAPESHIFT`, "Not while shapeshifted" ([SpellDefines.h](https://github.com/cmangos/mangos-classic/blob/master/src/game/Spells/SpellDefines.h#L46), line 46 when read on 17 Nov), and TrinityCore names it `SPELL_ATTR0_NOT_SHAPESHIFTED` ([SharedDefines.h](https://github.com/TrinityCore/TrinityCore/blob/master/src/server/game/Miscellaneous/SharedDefines.h)).
  - **What the cores do with it:** in both cores' shapeshift check (cmangos `GetErrorAtShapeshiftedCast` in [SpellMgr.cpp](https://github.com/cmangos/mangos-classic/blob/master/src/game/Spells/SpellMgr.cpp#L389), line 389, TrinityCore `SpellInfo::CheckShapeshift` in [SpellInfo.cpp](https://github.com/TrinityCore/TrinityCore/blob/master/src/server/game/Spells/SpellInfo.cpp)), a spell with the bit fails in any form that acts as shifted, unless the spell's own stance mask names that form.
  - **What we can't rule out:** the stance masks (the `SpellShapeshift` table) aren't in our extraction, so one exception is possible. Moonkin Form with Thorns is the likeliest; #454 says how to check.
  - **Moonkin Form is that exception:** a druid in Moonkin Form casts all of our druid buffs (Mark of the Wild, Gift of the Wild, Thorns) without leaving the form (the owner, 18 Nov, #485). So buff mode's key casts them there, with "Fast-cast buffs in form" off.
  - Omen of Clarity (16864) doesn't have the bit: its `Attributes_0` is `0x40`, passive (#452).
- **What the game does:** in travel form, buff mode's Thorns press pulled the owner out of the form (in game, 1.4.1, 17 Nov, #326). The macro is a plain `/cast`, so the game unshifted the druid itself, through the `autoUnshift` setting. Blizzard forum threads, read from search results only, say the setting is on by default, and that with it off the game refuses instead.
- **Which forms:** the 1.12.1 form numbers (cmangos-classic's `ShapeshiftForm`, "checked for 1.12.1", in [SpellDefines.h](https://github.com/cmangos/mangos-classic/blob/master/src/game/Spells/SpellDefines.h)) are Cat 1, Tree 2, Travel 3, Aquatic 4, Bear 5, Dire Bear 8 and Moonkin 31. The addon uses only Moonkin's (#485).
  - **Telling Moonkin apart** (#485): `GetShapeshiftForm()` is the stance bar's index, which depends on the forms a druid knows, so it can't name Moonkin. The addon reads the form's spell, the fourth answer of `GetShapeshiftFormInfo(index)` (Blizzard's stance bar reads it as the spell ID: `Blizzard_ActionBar/Shared/StanceBar.lua` line 69, Gethe/wow-ui-source classic_era at `4192ac6`, 1.15.9), and the form's number, `GetShapeshiftFormID()` (`MOONKIN_FORM = 31` in `Blizzard_FrameXMLBase/Classic/Constants.lua` lines 388 to 390, same commit; Blizzard's classic code never calls the function, so whether Forever's client has it is unknown). Forever's values are **unconfirmed**: [#488](https://github.com/CKozanecki/FriendlyForever/issues/488) says how to check.
  - Any `GetShapeshiftForm()` answer other than 0 counts as a form, and so does an answer the addon can't read (#452).
  - That 0 means caster form on Forever is **unconfirmed** (#454). If it's wrong, the key waits when it needn't: the safe side.
- **When the form changes:** `UPDATE_SHAPESHIFT_FORM` fires. Blizzard's code for Forever re-reads the form on it: [ActionBarController.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ActionBarController/ActionBarController.lua#L27) registers it at line 27, and its handler (line 80) updates the stance bar at line 83 (the `forever` branch of Gethe/wow-ui-source, read on 17 Nov). classic_era's `ActionButton.lua` does the same. The addon re-arms the button on it, and reads the form again at every press anyway.
- **The key and the click** (#452, the owner's decision of 17 Nov):
  - Buff mode lends its key to the button under a button name of its own, `BuffModeKey` (`SetOverrideBindingClick(owner, true, key, button, "BuffModeKey")`, #452).
  - Blizzard's `SecureButton_GetButtonSuffix` ([SecureTemplates.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua#L101-L117), lines 101 to 117 on the `forever` branch, read on 17 Nov; classic_era's is the same) gives `"1"` for `LeftButton` and `"-" .. name` for any name that isn't a mouse button's, and the action is looked up under that suffix. So a key press finds `*type-BuffModeKey`, and a click finds `*type1`.
  - Neither falls back to the other. With no type attribute, a press does nothing (`PerformAction`, [SecureTemplates.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua#L730-L731) lines 730 and 731 on the `forever` branch).
  - The addon writes the key's attributes only when the key may cast, and changes no binding when the form changes (#452).
  - Blizzard's code for Forever settles the button's side. That the game client passes the name a `CLICK` binding gives through to the button is **unconfirmed** (#454).
- **Key Bindings sections** (#509): Blizzard's code for Forever (`Interface/AddOns/Blizzard_SettingsDefinitions_Frame/Keybindings.lua`, Gethe/wow-ui-source at `aff0d8cd`, 1.60.1, the UI simulator's pin) titles a binding's section by the global its `category` names (`GetBindingCategoryName`, lines 220 to 226), else the raw text, and opens a section for any category it hasn't seen, after Blizzard's own (`AddBindingCategory`, lines 235 to 240). Forever loads it with the `Mainline` overrides. So both bindings use `category="BINDING_HEADER_FRIENDLYFOREVER"`, and the addon sets that global to "Friendly Forever". A `header` attribute does nothing there. Keys are looked up by the binding's name, so a category change keeps them. That the section shows in game is **unconfirmed**: [#511](https://github.com/CKozanecki/FriendlyForever/issues/511).
- **Indoors** (#510): `IsIndoors()` returns a non-nilable bool (`Blizzard_APIDocumentationGenerated/PlayerScriptDocumentation.lua`, same commit). The addon reads it, and the zone's name, at each arming of the buff button, and relies on no event. That a refused shift back clears once you walk outdoors is **unconfirmed** in game: [#511](https://github.com/CKozanecki/FriendlyForever/issues/511).

## Back into your form (#495)

From #495 (19 Nov 2026). With "Fast-cast buffs in form" on, buff mode offers your form back once everyone who needed a buff when you left the form is done (you, your group, and the strangers and passers-by then on the list), before anyone who turns up later (the owner's decisions on #495 and #510).

- **Which forms:** Cat Form, Bear Form, Dire Bear Form, Travel Form and Ghost Wolf (the owner: cat, bear, travel and Ghost Wolf; Moonkin never leaves its form, #485). Aquatic Form isn't one of them.
- **Their spells:** Bear 5487 and Dire Bear 9634 are Forever's own: `BEAR_FORM_SPELL_ID` and `DIRE_BEAR_FORM_SPELL_ID` in `Blizzard_ActionBar/Shared/SpellFlyout.lua`, lines 6 and 7 (Gethe/wow-ui-source, `forever` branch, 1.60.1.70959). Cat 768, Travel 783 and Ghost Wolf 2645 are Vanilla's (cmangos/mangos-classic, `sql/base/dbc/original_data/Spell.sql`). No Forever source names those three: **unconfirmed** ([#498](https://github.com/CKozanecki/FriendlyForever/issues/498)).
- **Reading the form:** the form's spell is the fourth answer of `GetShapeshiftFormInfo(index)`, as Blizzard's stance bar for Forever reads it (`StanceBar.lua` lines 70 and 155, same branch). `GetShapeshiftFormID` isn't called anywhere on that branch. The addon uses it only to say no: a number it gives that isn't the form's (Cat 1, Travel 3, Bear 5, Dire Bear 8, Ghost Wolf 16, cmangos-classic's 1.12.1 `ShapeshiftForm`) means no return. A shaman's Ghost Wolf also counts by its aura (#466). Anything unreadable means no return.
- **The macro:** `/cast !<form>`. In Classic, `!` keeps a form, stance or aura on when it is already on. The only sources are Blizzard forum posts: **unconfirmed** (#498). The addon offers the form only while you're in none, so the `!` is a second guard.
- **Leaving for a buff, or by hand:** the addon can't see why a form ended. A form left within 3 seconds of a buff press made in it counts as left for the press (`BuffButton.LEAVE_SECONDS`). Any other change of form drops the return (#495).
- **A cast that takes time:** in Classic, Ghost Wolf takes 3 seconds to cast (2 with Improved Ghost Wolf); druid forms are instant. While a shift back is being cast, the button offers nothing, so a scroll meanwhile can't be refused or land once you're back. A cast cut off (you moved) offers it again at once, on `UNIT_SPELLCAST_INTERRUPTED` or `UNIT_SPELLCAST_FAILED_QUIET`. Forever's cast time, and which of the two events a cut-off cast sends, are **unconfirmed** (#498).
- **The order of the game's events:** when a buff takes you out of a form, the addon expects the form change (`UPDATE_SHAPESHIFT_FORM`) before the buff's `UNIT_SPELLCAST_SUCCEEDED`. In the other order, a trigger's buff mode could turn itself off at that success, before the return is remembered, and no form would be offered. Nothing would cast wrongly. **Unconfirmed** (#498).
- **A refusal:** the addon shows the game's own words, so their exact text (Travel Form indoors, say) isn't needed (#495).

## PvP flags

- Inside a dungeon or raid, once everyone in the group is inside, it is safe to buff a player flagged for PvP, because nobody can attack you there. That is the only time it is safe to buff a flagged player. Source: the owner, 2026-11-13 (#306). Buff mode follows it (`GroupBuffs.lua`'s `FlaggedMayBeBuffed`), and so does buff back for a favour owed to a member of your group (#316, the owner, 2026-11-14: `Offers.lua`'s `ChooseBuff` asks the same function); a flagged player outside your group is never offered one. Everywhere else, battlegrounds and arenas included, neither buffs a flagged player unless you're flagged too. "Everyone is inside" is read as buff mode's dungeon wait reads it (#256): each member connected and shown by the game, in an instance `IsInInstance()` calls `"party"` or `"raid"`. A member outside your dungeon or raid reads as not visible: **confirmed in game** (owner, 2026-11-14, [#257](https://github.com/CKozanecki/FriendlyForever/issues/257#issuecomment-6869402459)), so they never count as inside. `IsInRaid()`, which says whether to read `raid1..40` or `party1..4`, is believed only when those slots agree with it ([#335](https://github.com/CKozanecki/FriendlyForever/issues/335)): when it says a raid, one of `raid1..40` must read as you (`UnitIsUnit`), and when it says not, `raid1` must read as not existing. If they disagree, or either can't be read, nobody is taken to be inside. Buff mode's group look (`GroupBuffs.Next`) applies the same check ([#346](https://github.com/CKozanecki/FriendlyForever/issues/346)): an answer the slots disagree with is treated like one that can't be read (#322), so `Next` isn't settled and offers no group version. Buff mode's triggers read the group through the same check ([#359](https://github.com/CKozanecki/FriendlyForever/issues/359): `GroupBuffs.RaidAnswer`), and while it fails they forget nobody they remember. So do "My Blessings in this raid", forgotten on a believable "not a raid" ([#368](https://github.com/CKozanecki/FriendlyForever/issues/368)) or, on a look that can read it, a new leader or most of the members at the choice gone ([#376](https://github.com/CKozanecki/FriendlyForever/issues/376)), and the tank check's "outside a raid" (#368). After a login or reload, buff mode notes who is missing a buff only once `IsInGroup()` can be read too ([#370](https://github.com/CKozanecki/FriendlyForever/issues/370)). Without that check a party taken for a raid would count everyone as inside, and a raid taken for a party would look only at your own subgroup. Still **unconfirmed**, each now on the safe side: whether a member inside but far away reads as visible (if not, the rule waits for them); the exact `IsInInstance()` answer (if it differed, the rule would never turn on); and the exact `IsInRaid()` answer (a wrong one keeps the rule off, #335). [#257](https://github.com/CKozanecki/FriendlyForever/issues/257) says how to check all three in game.

## Frame levels and mouse clicks (#427)

Researched for the options dropdowns (the owner's 1.3.3 report: a click on a list row closed the list without saving). Sources are Blizzard's UI code on GitHub (Gethe/wow-ui-source, branches `forever`, `classic_era`, `live`) and wiki snippets; warcraft.wiki.gg itself could not be read from a cloud session.

- **Mouse focus:** the frame that takes a click is the mouse-enabled one under the cursor with the highest strata, then the highest frame level. Confirmed: a Blizzard developer's 2005 post, quoted on Wowpedia's "How the user interface is rendered". A Button takes the mouse by default; a plain Frame only after `EnableMouse(true)`. Source: https://wowpedia.fandom.com/wiki/How_the_user_interface_is_rendered (#427).
- **Level never beats strata:** frame level orders frames only within a strata (the wiki's "UI rendering process" page, https://warcraft.wiki.gg/wiki/UI_rendering_process; #427).
- **Default level:** a child is one level above its parent ("UIParent's level is 1, children of UIParent are at level 2", the `SetFrameLevel` wiki page, https://warcraft.wiki.gg/wiki/API:Frame_SetFrameLevel), so siblings made one after another share a level (#427).
- **Tied siblings:** no source says which of two overlapping siblings at the same strata and level takes the click. Treat it as undefined, never as "the later one". This is the bug: `Dropdown`'s full-screen catcher and its rows were made from the same list, so they tied (#274, #427). The fix gives the rows an explicit level two above the catcher's, and sets it again each time the list opens.
- **Forever's Settings window:** `SettingsPanel` is declared `frameStrata="HIGH"` and `toplevel="true"`, and its Lua calls no `SetFrameLevel`, `Raise` or `SetToplevel` (all three branches, so Forever matches Classic Era). It reparents an addon's canvas with `SetParent`. The options pages are canvases the Settings window adopts (`Settings.RegisterCanvasLayoutCategory`, `Options.lua`), so they sit in that HIGH, toplevel panel, and its code changes none of their levels. (`Window.lua` is only the export, import and bug-report text window.) The dropdown's list sets `DIALOG` itself, which puts it above every frame in the panel whatever their levels. Not found in any source: whether `SetFrameLevel` on a parent moves its children, and whether strata is inherited at `SetParent`; so the addon never relies on either (#427).
- **Check in game (not confirmed):** open `/fstack` over an open dropdown list and look at the order of the rows and the catcher (#427). It is also the missing in-game check of #283's "click a row: saved and closes".
