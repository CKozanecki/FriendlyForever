# UI simulator: known quirks

CONTRIBUTING.md's [UI simulator](../CONTRIBUTING.md#ui-simulator) section says what the simulator runs, where its output is and the safety rules for its workflow. This file adds only its known quirks and their workarounds, so the next session doesn't rediscover them. Where the two differ, CONTRIBUTING.md wins and this file is fixed.

The simulator is [wow-ui-sim](https://github.com/Osso/wow-ui-sim), adopted in #49 and #53. Unless a line says otherwise, the quirks below are at `936d5f5` (#160), the pinned commit on the simulator's `master`, on its Forever profile, and come from **#100**, which collected them for upstream (Osso/wow-ui-sim#13). The maintainer fixed most of them in `d907b88` and `ac893c6`, and more since. #154 and #160 checked each against the source and in a run, and dropped the workarounds the fixes cover. When the pin moves (#53's rules), check each one again and update this file and #100.

**The run checks them for you.** The first scenario in `uitests/scenarios.lua` prints a `FACT sim` line for each quirk it can ask the simulator about (the client, the starting party and buffs, spell names and range, the caster of an added buff, when `PLAYER_REGEN_DISABLED` arrives, anchors, wrapping, text height), each options tab says how many of its rows read out of place before the layout is settled, and the last scenario lists every action the client blocked or forbade an addon during the run. Read those lines in a pin move's first run before reading the source: a line that changed is a quirk that changed.

Several workarounds live in `uitests/button_states.lua`, which sets up the buff-back button's real states (#83, #96). Its header lists them.

## Blizzard's own errors

These come from Blizzard's UI code in the simulator, not from the addon. They're reported, not failed; `States.Watch` (`uitests/button_states.lua`) sorts errors by whether the addon's own error count went up (#96).

On the Forever profile (`936d5f5`), seen in #160's runs:

- `Blizzard_AchievementUI.lua:986`: `GetTrackedIDs` is nil, many times a run. It fills the first 60,000 bytes of `run-tests.log`, which is all the job log shows of it; the digest and the summary are taken from the whole file (#160).
- `PlayerFrame.lua:352`: `GetUnitPvPIndicatorDisplayInfo` is nil (#160).

Both are gaps in the simulator's Forever profile, noted on #100 for the contribution project.

Not seen at `936d5f5` on the Forever profile, in the part of the log a session can read. All four were in `main`'s last run at `ac893c6`. Upstream's fixes since then are the likely reason for the first three (#160 lists the commits); Forever's different UI code may be another:

- `CompactArenaFrame.lua:318` ("secret access requires an untainted caller", when the party changes) and "AuraButton cannot be created by addons": events from `A_Admin` now start untainted (#100, 11).
- `AddonList.lua:899` ("table index is nil"): `ADDON_ACTION_BLOCKED` now names the addon (#100, 13).
- `Audio.lua:179` (`GetAvailableOutputDevices` is nil): fixed by our contribution, merged upstream on 2026-10-31 (#100); the function exists now (the `FACT sim` line).

Fixed earlier, by `ac893c6`, which stubs the missing functions with chosen defaults: `IsReplacingUnit` (`TargetFrame.lua:169`), `C_VoiceChat.CanAccessSettings`, `FlashClientIcon` (`LowHealthFrame.lua:176`) and `UnitPowerDisplayMod` (`ShardBar.lua:45`) (#100, 9, 10, 12).

## Screenshots

CONTRIBUTING covers what they show (our text, layout and colours, without Blizzard's art or WoW's fonts). Also:

- There's no published image at our pin, so the workflow's `simulator` job builds the simulator, with its renderer, in a sandbox, and both other jobs run that build (#53, #154). A cold build takes about 10 minutes; any edit to `ui-sim.yml` is one.
- The screenshot step's time limit (#309): the 27 shots of a pass each take about 8 s, but one that reaches its own 180 s limit takes about 200 s with its checks and clean-up, so a worst-case pass is about 90 minutes. No shot starts after `SHOT_CUTOFF` (4200 s into the step) in either pass, which keeps the last one inside the step's 75 minutes. A worst-case first pass therefore costs the second pass's shots (named `skipped, out of time` in the log); a normal run takes about 8 minutes. `spec/repo_spec.lua` counts the shots in `shoot_all` and checks the comment's numbers, so adding a shot means updating them.
- It renders off screen with software GL, as the runner's user with `HOME` in `/tmp`, since with every capability dropped root can't write the PNG; `xvfb-run` sat idle under Docker (#53, `ui-sim.yml`).
- Between two runs of the same code, the simulated buff timers at the top right differ (#91), and the typeface can: with no game fonts, the simulator draws every WoW font in the first system face its font library lists (`first_system_family_name` in `src/render/font.rs`, the same at `ac893c6` and `936d5f5`), and nothing fixes which of the render image's DejaVu faces that is. #160's runs on `b51c40b` and `3832643` drew sans, and its run on `8a074c3` serif, with only the spell data proxy's settings and docs changed between them. So when every letter differs between two sets, compare the faces first; when the face is the same, treat other differences as real. The `ui-sim` and `screenshots` jobs run on separate runners and each picks its own, so the `LAYOUT` widths can follow a different face than the shots, and differ between runs too (#310: one row 230 px in one run and 226 in another). Since `936d5f5` the simulator takes `WOW_SIM_FALLBACK_FONT=<font file>` to pin the face (upstream's `5eb2fd993`). The workflow sets it on every `wow-sim` run (the scenarios, the sized layout passes and the shots) to `RENDER_FONT`, the render image's `DejaVuSans.ttf`, and the image build fails if that file is missing, since the simulator only warns and falls back; `spec/repo_spec.lua` checks each run has it (#310). So since #310 both jobs, and every run of one commit, draw and measure in the same face, and a run's `LAYOUT` widths compare with another's from the same pins. The first run after #310 changes every shot's face once (to sans), and its widths may differ from earlier runs' by the 4 px #310 saw (230 against 226) or so; compare against runs made after it. Runs from before #310 still differ between jobs by whichever face the image listed first. Two runs of one commit still differ a little in the shots: the buff timers at the top right and the chat clock, and, from some runners, one colour level (a difference of 1 in a channel) thinly over most text, about 400 to 1,300 px a shot (software GL rounds differently on different CPUs; seen between #324's runs on `d413d64` and `b9ca654`). Ignore differences of one level; a face change is about 16,000 px in a shot (#324).
- A before set for comparing is hard to come by: each run replaces its PR's `ui-screenshots/pr-<n>` branch, a closed PR's branch is deleted, and `main`'s runs keep theirs only as an Actions artifact, which a cloud session's network can't reach (#115, `ui-sim.yml`). Save the PNGs of an earlier run before pushing again, or use another open PR's branch.
- The minimap and the button's border aren't drawn, so the minimap button's icon floats alone (#93).
